# Руководство по разбору обновлений MCP в HISTOR

[English](upgrade-brief.md) · [Русский](upgrade-brief.ru.md) · [Español](upgrade-brief.es.md) · [Français](upgrade-brief.fr.md) · [中文](upgrade-brief.zh.md)

Локальный прототип связывает изменения MCP-инструментов с вашими рабочими сценариями. Он читает
два сохранённых наблюдения для каждой зависимости и создаёт `report.md` и `report.json`: какие
определения изменились, какие выбранные инструменты затронуты и что перепроверить.

Используйте текущие локальные исходники прототипа. Разбор детерминированный, без LLM,
сетевых запросов, настроек production, базы данных и ключей.
Инструкции внутри tool descriptions остаются данными. Изменение определения — повод проверить
сценарий; оно само по себе не доказывает поломку или опасность сервера.

## Запустить и проверить пример

Нужен Python 3.11 или новее. Из каталога `histor/` в этом workspace:

```bash
python3 --version
python3 -m histor upgrade-brief \
  --lang ru \
  --watchlist examples/upgrade-brief/watchlist.ru.json \
  --out-dir ../output/histor-upgrade-brief-example/ru
python3 examples/upgrade-brief/verify.py \
  --out-dir ../output/histor-upgrade-brief-example
```

Если подходящий интерпретатор — `.venv/bin/python`, замените им `python3` во всех командах.
Для офлайн-примера установка пакетов не нужна. Проверка дважды запускает каждый из пяти
watchlist, сверяет ожидаемые изменения и статусы сценариев, побайтовую повторяемость отчётов
и неизменность входных файлов. Успех обозначается `PASS` и кодом выхода `0`, ошибка проверки —
кодом `1`. В каждой языковой папке будут `report.md` и `report.json`; повторный запуск заменяет
эти сгенерированные файлы.

Проверка также дважды запускает команду без `--lang` и требует побайтового совпадения с явным `--lang en`: всего 12 офлайн-запусков CLI.

Пример полностью синтетический. Он показывает изменения обязательных полей, типов, описаний,
выходной схемы и annotations, удаление используемого инструмента, смену протокола и неуспешное
наблюдение. Шесть снимков описывают три зависимости и четыре сценария. Никакие пакеты не
устанавливаются и серверы не запускаются; инструменты не вызываются. Конкретные перепроверки
описаны в [пошаговом примере](../examples/upgrade-brief/README.ru.md).

Руководство, инструкции примера, заголовки watchlist и описания сценариев доступны на пяти языках.

## Выбрать язык отчёта

`--lang` принимает `ru`, `en`, `es`, `fr` или `zh`. По умолчанию используется английский (`en`) в CLI, Python API и при выборе языка рендерером без поля `language`. Параметр выбирает язык служебных заголовков и пояснений Markdown,
чеклистов инструментов и сценариев, текстов проверок и ограничений в JSON. Поле `language`
в JSON сохраняет выбор. Имена полей, коды статусов, диагностические причины, ID, схемы и хеши
остаются прежними.

Заголовок watchlist, описания сценариев и фрагменты исходных определений сохраняются как
переданы. Для подписей на нужном языке выберите соответствующий watchlist примера;
`--lang` не переводит ваши входные данные автоматически.

## Описать свои зависимости

Создайте отдельную папку с `watchlist.json` и снимками. Пути к снимкам задаются относительно
watchlist и должны оставаться внутри этой папки. Сетевые URL вместо путей, выход через `..`
и symlink наружу не принимаются.

```json
{
  "format": "histor.upgrade-watchlist/v1",
  "title": "Наша исследовательская команда",
  "dependencies": [{
    "id": "our-research-server",
    "before": "snapshots/before.json",
    "after": "snapshots/after.json",
    "tools": ["search_docs"],
    "workflows": [{
      "id": "weekly-review",
      "description": "Подготовить еженедельный обзор",
      "tools": ["search_docs"]
    }]
  }]
}
```

Списки выбранных инструментов и инструментов каждого сценария должны быть непустыми. Каждой
зависимости нужен хотя бы один сценарий. Сценарий может ссылаться только на выбранные инструменты
своей зависимости. При переводе подписей сохраняйте ID зависимостей и сценариев, имена
инструментов. `before` или `after` допускают `null`: при отсутствии наблюдения соответствующий
вывод останется неизвестным. Для сравнения `targetId` снимка должен совпадать с `id` зависимости.

Запустите разбор своего набора из каталога `histor/`:

```bash
python3 -m histor upgrade-brief \
  --lang ru \
  --watchlist /path/to/bundle/watchlist.json \
  --out-dir /path/to/report
```

## Сохранить наблюдение HTTP сервера

Снятие снимка — отдельное явное сетевое действие. Для `capture` нужны зависимости HISTOR из
`pyproject.toml`. Если они ещё не установлены, подготовьте окружение из текущих исходников;
установка может обращаться к индексам пакетов:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

Для публичного HTTP MCP endpoint укажите его реальный URL и новое имя файла:

```bash
.venv/bin/python -m histor upgrade-brief capture \
  --url https://your-public-server.example/mcp \
  --target-id our-research-server \
  --out /path/to/bundle/snapshots/before.json
```

Домен `.example` и пути `/path/to/` — шаблоны. Повторите команду после обновления с новым именем
`after.json`, затем сформируйте офлайн-отчёт.

`capture` использует защищённый reader HISTOR: discovery, при необходимости старую инициализацию
и все страницы `tools/list`. Инструменты не вызываются. Локальные/private адреса по умолчанию
запрещены; для собственного стенда их можно явно разрешить `--allow-private`.
Команда не устанавливает и не запускает MCP-пакеты. `--timeout` по умолчанию равен 20 секундам;
допустимое значение — больше 0 и не больше 300.

Этот первый collector работает без auth и отказывается от URL с userinfo, query или fragment.
Существующий файл снимка никогда не перезаписывается. Код выхода `0` означает сохранённый
полный снимок, `1` — сохранённое неуспешное наблюдение, `2` — неверный ввод или невозможность
сохранить файл. Неуспешное наблюдение не содержит пустого списка, выдаваемого за успех.

Снимок collector — неподписанное локальное свидетельство. Хеши отчёта позволяют заметить
изменение входных файлов, но не удостоверяют, кто их создал. Удалённый сервер может показывать
другой список при других правах доступа, запуске или времени наблюдения.

## Формат наблюдения

```json
{
  "format": "histor.upgrade-observation/v1",
  "targetId": "our-research-server",
  "status": "ok",
  "observedAt": "2026-10-27T09:00:00Z",
  "packageVersion": null,
  "serverName": "our-research-server",
  "serverVersion": "1.2.0",
  "protocol": "2026-07-28",
  "extrasCoverage": "observed",
  "launch": {"transport": "streamable-http", "endpoint": "https://your-public-server.example/mcp"},
  "tools": [{"name": "search_docs", "description": "Search documents", "inputSchema": {"type": "object"}}]
}
```

Успешному наблюдению нужен полный массив `tools`. Сохраняйте фактические время с часовым поясом,
протокол и условия запуска. Для удалённого endpoint `packageVersion` может быть `null`.

Для импорта из HISTOR API сохраняйте полные определения инструментов нужного наблюдения, его
время и происхождение. Локальная реализация `/api/v1/servers/{id}` содержит
`timeline[].protocolVersion`; при наличии переносите его в snapshot как `protocol`.
Старый или развёрнутый API может не возвращать это поле: сохраняйте пробел в данных.
Автоматического импортера API у прототипа нет. Версию пакета нельзя подменять версией, которую
сервер сообщает о себе. Дополнительные поля инструмента HISTOR хранит отдельно в `toolExtras`:
при подготовке полных snapshots их нужно присоединить к инструментам по имени, если они относятся
именно к этому наблюдению. Это позволит увидеть изменения annotations и vendor metadata.
Текущие `tools` и extras нельзя использовать как старый снимок по дате timeline.

Если исходник содержит только четыре поля MTL/1, задайте `extrasCoverage: "unknown"`.
Такой снимок позволяет сравнить основные определения, но не устанавливает изменения annotations
и других дополнительных полей. Текущие extras не подставляются вместо исторических. Отчёт
сохранит найденные различия и пометит общую сопоставимость как неизвестную. Значение
`observed` означает, что в файле представлены все дополнительные поля, показанные в этом
наблюдении; это также значение по умолчанию для прежних локальных v1-снимков.

`launch` следует сохранять одинаково для одинаковых условий запуска. Отчёт выводит только
его хеш и известный тип транспорта; команды, аргументы и значения env в отчёт не копируются.
Полные исходные snapshots всё равно могут содержать чувствительные данные и остаются у вас.

## Как читать результат

- `changed`: в сопоставимых наблюдениях изменились определения; смотрите выбранные инструменты
  и чеклист сценария.
- `unchanged`: в сопоставимых наблюдавшихся определениях изменений нет. Поведение не проверялось.
- `context_changed`: изменились известные условия запуска или протокол. Разницу нельзя целиком
  приписать обновлению пакета.
- `unknown`: недостаточно успешных наблюдений, выбранный инструмент не найден с обеих сторон
  или сопоставимость не установлена, в том числе при неизвестном покрытии extras. Обратный порядок
  дат также не трактуется как обновление.

Статусы сценариев: `retest`, `no_observed_change`, `unknown`. Зависимость может измениться за
пределами выбранных инструментов; планируйте проверки по статусам отдельных сценариев.
`fieldCoverage` принимает `full`, `core-only` или `none`. Найденные различия остаются видимыми,
даже если общая сопоставимость неизвестна. Annotation hints остаются заявлениями сервера.

Версии и хеши исходных файлов сохраняются в JSON. Разбор использует явно указанную связь
«сценарий → инструмент» и не угадывает смысл вашей работы. Размер model-facing JSON измеряется
в UTF-8 байтах; это не число токенов, сумма счёта или доказанная экономия. Полный JSON output
остаётся подробным свидетельством, а Markdown даёт порядок перепроверок.

## Ограничения и решение проблем

Ограничения прототипа: до 30 зависимостей, 128 выбранных инструментов и 64 сценариев на
зависимость, 2000 инструментов на снимок. Watchlist ограничен 256 000 байтами, снимок —
2 000 000 байтами. Дубликаты JSON-ключей, неизвестные поля формата, NaN и бесконечности,
неверные определения и структуры глубже 48 уровней или больше 100 000 узлов не принимаются.

Команда отчёта возвращает `0`, если отчёт создан, включая честные `unknown`, и `2` при неверном
вводе или ошибке записи. Существующий каталог отчёта можно использовать повторно: `report.md`
и `report.json` заменяются; перезапись входных файлов запрещена. При `No module named histor`
перейдите в каталог `histor/` с исходниками. При `unknown` изучите `limitations`, `sources` и
`fieldCoverage` перед решением об обновлении. Неизменность определений и успешная генерация
отчёта сами по себе не подтверждают корректность поведения или безопасность сервера.
